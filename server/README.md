# Safetics — бекенд

Spring Boot 4.1, Java 21, PostgreSQL 17, Flyway. Модульний моноліт.

## Що потрібно

- JDK 21
- Maven 3.9+ (або вбудований у IntelliJ)
- Docker Desktop (для локальної бази і для тестів через Testcontainers)

## Запуск

```bash
docker compose up -d
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
curl localhost:8080/actuator/health
```

Профіль `dev` додає ключ для JWT і демо-дані (`src/main/resources/db/dev`). Без профілю застосунок не стартує, поки не задано `SAFETICS_JWT_SECRET`: так демо-користувачі ніколи не потраплять на сервер.

У профілі `dev` також працює опис API: Swagger UI — http://localhost:8080/swagger-ui.html, JSON — `/v3/api-docs`. З нього веб генерує типи (`npm run api:generate` у `web/`). Без профілю `dev` опис вимкнений.

## Тести

```bash
./mvnw test
```

Тести піднімають окремий PostgreSQL у Docker (спільна основа — `AbstractIntegrationTest`):
- `TenantIsolationTest` — на рівні бази: компанія A не бачить і не змінює дані компанії B;
- `AuthApiTest` — через HTTP: вхід, cookie і Bearer, вибір компанії, дозволи, оновлення і вихід;
- `OpenApiDocsTest` — опис API на місці, обов'язкові поля позначені як required;
- `AttributeValidatorTest` — перевірка значень полів (без Spring);
- `AssetApiTest` — обладнання через HTTP: шаблон і категорії, валідація, ієрархія, версії, ізоляція, дозволи;
- `LastAdminProtectionTest` — компанія не лишається без адміна.

Обов'язкові поля відповідей позначаються `@NotNull`: тоді в згенерованому TypeScript вони не стають необов'язковими.

## Як влаштована мультитенантність

- Кожна таблиця компанії має `company_id` і політику Row-Level Security (`V3__row_level_security.sql`).
- Дві ролі в базі:
  - `safetics_owner` — власник схеми, під ним працює лише Flyway;
  - `safetics_app` — застосунок, без `SUPERUSER` і `BYPASSRLS`. Цю роль створює міграція `V1`.
- `TenantContext` зберігає поточну компанію і користувача для потоку.
- `TenantAwareDataSource` при кожному отриманні з'єднання з пулу пише їх у сесію PostgreSQL (`app.company_id`, `app.user_id`). Без контексту RLS не віддає жодного рядка.
- `TenantContextFilter` заповнює `TenantContext` з перевіреного JWT (`sub` — користувач, `cid` — компанія).

## Вхід

| Ендпоінт | Для кого | Що робить |
| --- | --- | --- |
| `POST /api/v1/auth/login` | веб | телефон + пароль → httpOnly-cookie `sft_access` (15 хв) і `sft_refresh` (30 днів), у тілі — сесія |
| `POST /api/v1/auth/refresh` | веб | нова пара cookie; старий токен оновлення відкликається |
| `POST /api/v1/auth/switch-company` | веб | вибір компанії, якщо їх кілька |
| `POST /api/v1/auth/logout` | веб | відкликає токен оновлення, видаляє cookie |
| `GET /api/v1/auth/me` | усі | поточна сесія: користувач, компанія, список компаній, дозволи |
| `POST /api/v1/auth/token`, `/token/refresh` | бот, мобільний | те саме, але токени в тілі; далі `Authorization: Bearer` |

- Дозволи ролі потрапляють у токен (`perms`) і перевіряються так: `@PreAuthorize("hasAuthority('audit.view')")`. Назви ролей у коді не перевіряються.
- Зміна ролі діє з наступним оновленням токена (до 15 хвилин).
- CSRF-токен не потрібен: cookie мають SameSite=Lax, а API приймає лише JSON.
- Приклад захищеного ендпоінта: `GET /api/v1/audit-log` (потрібен `audit.view`).

## Ролі компанії

| Роль | Що може |
| --- | --- |
| `admin` — Адмін | усе в компанії: налаштування, люди, довідники, журнал змін. Останнього активного адміна не можна понизити чи видалити (тригер у базі) |
| `director` — Керівник | як менеджер, але на всіх проєктах (`project.access_all`) |
| `manager` — Менеджер | замовники, проєкти, обладнання, рапорти на своїх проєктах |
| `worker` — Виконавець | обладнання, рапорти, чек-листи на своїх проєктах |
| `client_rep` — Представник замовника | перевіряє змінні рапорти (`report.review`): геолог, інженер чи інша людина замовника |
| `client_manager` — Менеджер замовника | затверджує місячний звіт (`monthly_report.approve`) |

Обмеження «лише свої проєкти» і «лише проєкти свого замовника» з'явиться разом з таблицями проєктів.

## Обладнання (в коді — assets)

- **Тип обладнання** (`asset_type`) має категорію: `primary` — основне, виконує послуги (бурова), або `auxiliary` — допоміжне (авто, табір, ємність ПММ). Тип задає поля (`fields`: ключ, назва за мовами, тип, одиниця, обов'язковість, min/max, варіанти), статуси і які типи можна вкладати. Типи змінюють власник і адмін (`catalog.manage`).
- **Об'єкт** (`asset`) — свердловина, установка, авто: номер, назва, статус, значення полів у `attributes` (jsonb). Значення перевіряє `AttributeValidator` за схемою типу; помилки повертаються по полях: `{"error": "validation_failed", "fields": {"attributes.dip": "too_large"}}`.
- **Шаблон** `resources/templates/exploration-drilling.json`: бурова установка, авто, табір, ємність ПММ. Свердловина — не обладнання, а послуга проєкту. Встановлення: `POST /api/v1/asset-types/install-template`. Наявні типи не перезаписуються. У профілі `dev` шаблон і демо-об'єкти додаються автоматично (`DevDataInitializer`).
- Зміна об'єкта вимагає `version`: якщо його вже змінили, відповідь `409 stale_version` (знадобиться для офлайн-правок).
- Об'єкти не видаляються, а архівуються. Усі зміни пишуться в журнал з тим, що саме змінилося.

## Платформа і користувачі

- **Адмін платформи** — прапорець `app_user.is_platform_admin`, у токені authority `platform.admin`. Видається лише SQL-командою:
  ```sql
  update app_user set is_platform_admin = true where phone = '+380...';
  ```
  Він бачить компанії та їхні членства (політики RLS з `app_is_platform_admin()`), але не дані компаній. API `/api/v1/platform`: шаблони, компанії, створення (компанія + перший адмін + шаблон), призупинення / відновлення. Кожна дія — у `platform_audit_log` (лише додавання). Компанія створюється в контексті нової компанії, транзакція починається вже всередині (`TransactionTemplate`), бо компанія передається в базу при отриманні з'єднання.
- **Шаблони** (`resources/templates`): розвідувальне буріння, буріння на воду, меблі, шиномонтаж, будівництво — типи обладнання й посади.
- **Користувачі компанії** — `/api/v1/users` (`staff.manage`): додати, змінити роль, вимкнути, відновити. Правило «не більше прав, ніж маєш сам» для старої й нової ролі; себе не змінити; останній адмін захищений; ролі порталу — лише через контактних осіб.

## Замовники і проєкти

- **Замовник** (`customer`) і **контактні особи** (`customer_contact`). Перегляд — `client.view`, зміни — `client.edit`. Замовника з активними проєктами не можна архівувати.
- **Вхід у портал** контактної особи: `POST /api/v1/customer-contacts/{id}/portal-access` з роллю `client_rep` або `client_manager` (`project.manage`). Вхід — за телефоном контактної особи. Якщо обліковий запис з цим телефоном уже є, додається лише членство, пароль не змінюється. Відкликання і архів контактної особи вимикають членство.
- **Проєкт** (`project`): замовник (необов'язковий), код, часовий пояс IANA, дати, статус `active` / `closed`. Зміни — `project.manage`.
- **Графік змін** (`shift_schedule`): версії «діє з дати». Зміни: код, назва, початок `HH:mm`, тривалість у хвилинах. Перевірки — `ShiftRules`: без перекриттів (і через північ), сумарно не більше 24 год. Нова версія — лише з майбутньої дати; поточну й минулі не змінити.
- **Доступ до проєкту** діє в RLS (`app_sees_project`): `project.access_all` (адмін, керівник) — усі проєкти; рядок у `project_access` — конкретний проєкт (автор проєкту отримує його автоматично); контактна особа з входом — проєкти свого замовника. Чужий проєкт для API — `404`. Таблиці, що належать проєкту, використовують `app_can_see_project(project_id)`.
- Учасники компанії для вибору доступу: `GET /api/v1/members`.
- Демо (`dev`): замовники Vale Exploration і Taziazet Gold, проєкти VALE-CRJ (2×12) і TZG-01 (3×8). Менеджер +380500000002 має доступ лише до VALE-CRJ, представник замовника +380500000003 бачить лише VALE-CRJ.

## Виконавці і призначення

- **Посада** (`position`, довідник компанії; шаблон дає готові): `projectRole` — `supervisor` / `storekeeper` / `none` (за нею правила знайдуть «супервайзера проєкту»), `supervisorCanAdd` — супервайзер може сам додати людину з цією посадою. Зміни — `catalog.manage`.
- **Виконавець** (`personnel`): штатний / субпідрядник / найманий, посада за замовчуванням, вхід у систему необов'язковий (`personnel.manage`). Вхід: `POST /api/v1/personnel/{id}/login` — роль не ширша за вашу (`403 role_exceeds_own`); якщо людина вже працює в компанії, прив'язується наявний вхід без зміни ролі.
- **Призначення** людей і обладнання на проєкт (`personnel_assignment`, `equipment_assignment`): дати включні, без кінця — безстрокове. Людина й основне обладнання — лише на одному проєкті одночасно; допоміжне — на кількох, але не двічі на тому самому. Перекриття не дає `exclude` у базі (`409 overlap`), зокрема з проєктом, якого користувач не бачить. Вибір обладнання: `GET /api/v1/projects/{id}/available-equipment` (вільне / зайняте до …). Лише обладнання верхнього рівня; дати — у межах проєкту. Людина з входом отримує доступ до проєкту.
- **Супервайзер** (зараз призначений на проєкт на посаду з `projectRole = supervisor`) додає людей без входу: `POST /api/v1/projects/{id}/crew`, лише посади з `supervisorCanAdd`.

## Послуги і задачі

- **Послуга** (`service`, тип — `service_type` з полями): свердловина, замовлення меблів, шиномонтаж. Статуси для всіх галузей: `planned → in_progress → completed`, `cancelled` (з причиною). Ведуть менеджер і супервайзер проєкту; замовник (портал, `service.plan`) — лише заплановані.
- **Задача** (`task`, тип — `task_type`): статуси за типом, кожен з категорією `new / active / done / cancelled`; власні поля; форма закриття (`closing_fields`); предмет — послуга або обладнання; зв'язки `blocks` / `relates`, підзадачі; історія `task_history` (лише додавання). Номер у межах компанії (`task_counter`).
  - В `active` / `done` не перейти, поки є незавершені задачі, що блокують; `done` — лише із заповненою формою закриття і (якщо тип вимагає) закритими підзадачами.
  - Тип із `sync_service`: задача в роботі → послуга «в роботі», завершена → «завершено», значення форми закриття з ключами полів послуги (`actualDepth`) записуються в послугу.
  - Права: менеджер і супервайзер проєкту — усе; виконавець — статус, дати й форма закриття своїх; повернути / скасувати — лише менеджер і супервайзер. Портал задач не бачить (`task.view` і RLS через `app_has_permission`).

## Правила, закладені з першого дня

- Гроші зберігаються цілими числами в мінімальних одиницях валюти.
- Рухи складу не змінюються, помилки виправляються лише сторнуванням.
- Ціна копіюється в наряд у момент його створення.
- У коді перевіряється лише дозвіл (`stock.write_off`), ніколи назва ролі.
- Затверджений рапорт заблокований, зміни вносяться лише коригувальним записом.
- Журнал змін (`audit_log`) — лише додавання.
